# Scripting Is Fun

**Display name:** `scripting is fun`
**Belongs to:** the `plan` workspace → `workflows` → `marketing package`
**Use:** narration and shot-writing companion for the showcase recording plan

A good demo script is not a tour of every API. It is a small promise, a visible action, and
an observable result. The script should sound confident about what the repository does and
plain about what it does not do.

## The three-beat pattern

1. **Problem:** “I need to ___, but ___ is hard to see/control/reverse.”
2. **Action:** name the tool and perform the smallest real operation.
3. **Proof:** hold on the returned result, changed frame, state report, or undo report.

Use one idea per shot. Let the screen prove the sentence; do not narrate a feature that is not
visible in the take.

## Reusable script cards

### Card A — adaptive discovery

**On screen:** a plain-language need, then the ranked registry result.

> “Instead of loading every tool into context, I’ll describe the job. SkeletonKey searches the
> advertised catalog, shows the contract and risk, and turns the match into a replayable plan.
> The important part is that this is the tool the host can actually run on this machine.”

**Tool beats:** `profile.probe`, `registry.search`, `registry.describe`, `planner.plan`.

### Card B — safe change

**On screen:** a disposable fixture, a targeted patch, then the undo result.

> “This edit is intentionally small. I can see the match before changing it, apply a targeted
> patch, and keep the journal receipt. Now I’ll undo the task and show the original file again.
> The safety feature is not a warning after the fact; it is part of the result.”

**Tool beats:** `fs.search`, `fs.read`, `fs.patch`, `fs.journal_list`, `fs.undo_task`.

### Card C — live HMR

**On screen:** `orbital.py`, the live preview, one REPL change, and a file save.

> “This is a running Python program, not a pre-rendered animation. I’ll change the colour in
> the live namespace, then save the file. The scene updates without a restart, and the counter
> and live state remain visible. If the new source is broken, the panel keeps the old frame and
> reports the error instead of pretending the reload worked.”

**Tool beats:** `live.start`, `live.serve`, `live.status`, `live.repl`, `live.render`.

### Card D — the viewport and catalog

**On screen:** the live panel at `/`, the catalog at `/tools` or a standalone catalog.

> “The live panel makes the running demo visible. The catalog explains the tools around it:
> capabilities, risk, gates, and relationships. The mounted catalog is useful for a private
> development viewport, but it is not a public website injector. For sharing a read-only view,
> I use the standalone catalog or an exported HTML file.”

**Tool beats:** `live.serve` with `mount_tools`, `sk viz --serve`, `sk export viz-html`.

### Card E — honest integration loading

**On screen:** the simple zero-dependency integration and its health result.

> “An integration is more than a name in a list. I can discover its manifest, inspect its
> capabilities, validate it, and check health before loading it. If an optional dependency is
> not installed, the result says so; the demo does not manufacture a green check.”

**Tool beats:** `integrations.discover`, `integrations.list`, `integrations.describe`,
`integrations.validate`, `integrations.health`, `integrations.load`.

### Card F — publish preparation without secrets

**On screen:** fake placeholders and a dry-run report only.

> “Publishing needs platform knowledge and release checks, but credentials should not be part
> of the demo. I’ll inspect the target, scan the placeholder locations, and run a dry-run. The
> plan names every file that would change. A missing binding refuses the whole operation instead
> of producing a half-published result.”

**Tool beats:** `pub.platforms`, `pub.packaging`, `pub.testers`, `pub.placeholders`,
`pub.inject` with `dry_run: true`.

## First clip: a complete short script

**Working title:** *Edit a live scene without a restart*
**Target length:** 75–90 seconds
**Source:** `examples/live_hmr/orbital.py`
**Tools:** `live.start`, `live.serve`, `live.status`, `live.repl`, `live.render`

### Shot list

| Time | Picture | Voiceover / on-screen copy |
| --- | --- | --- |
| 0:00–0:08 | Title and the source file. | “What if a demo could change while it is running, without losing its state?” |
| 0:08–0:20 | Start the program and open the preview panel. | “I’m starting the repository’s live HMR example and serving its preview panel.” |
| 0:20–0:35 | Orbital scene with its counter and HUD. | “The frame is generated by Python. The counter, orbit, and handler state are all live.” |
| 0:35–0:49 | Run a small REPL assignment such as changing `hue`; show the frame change. | “First I’ll change one value in the live namespace. The panel re-renders, and the process stays alive.” |
| 0:49–1:06 | Save a safe source edit; show the watcher update and counter continuing. | “Now I’ll save the file. The watcher compiles the new source, patches it in place, and preserves the state that belongs to the running session.” |
| 1:06–1:18 | Force a render or show status; pause on the result. | “The result is visible immediately, and the status tells us exactly which program and frame we are looking at.” |
| 1:18–1:28 | End card with source path and limitations. | “This is a live HTML/SVG preview, not a video player or uploader. The recording is made separately so the behavior stays reproducible and honest.” |

### Take notes

- Keep the panel private while it is showing the REPL; it executes code.
- Use the disposable workspace and a fake/demo scene.
- Capture the source commit, toolset digest, Python version, and the exact REPL statement in the
  sidecar.
- If the watcher or optional frontend is unavailable, show the returned error or fallback and
  mark the take accordingly.

## Words to prefer and avoid

| Prefer | Avoid unless it is actually implemented and shown |
| --- | --- |
| “live preview,” “rendered frame,” “read-only catalog,” “replayable plan,” “journaled undo” | “video player,” “streaming playback,” “embed anywhere,” “inject into any domain,” “one-click upload” |
| “the tool is advertised on this host” | “the tool always exists” |
| “the optional backend is unavailable, so the fallback is shown” | “production-ready” when only a mock/fallback was exercised |
| “private development mount” | “safe public embed” for the merged live panel |

## Thumbnail, title, and description templates

**Title:** `[Outcome] with [tool or surface] — SkeletonKey demo`

**Thumbnail copy:** two to five words, such as `NO RESTART`, `UNDOABLE EDIT`, or `TOOLS EXPLAINED`.

**Description:**

> Reproducible demo from `<commit>`. Shows `<tool sequence>` using `<demo source>`. The capture
> uses `<host profile>` and `<toolset digest>`. Limitations: `<fallback, private panel, or
> missing player/uploader note>`. This clip demonstrates behavior in the repository; it is not
> a claim that the project hosts or uploads video.

## Final script check

Before recording, read the script while looking only at the intended capture window:

- Can every noun in the narration be pointed to on screen?
- Does every named tool appear in the actual sequence?
- Does the clip show a result rather than only an invocation?
- Does the script say “preview” when the output is a preview?
- Are missing tools, optional dependencies, and security boundaries stated where relevant?
- Can another person reproduce the take from the sidecar and source commit?

If the answer is yes, scripting is fun: the words get out of the way and the tool does the
selling.
